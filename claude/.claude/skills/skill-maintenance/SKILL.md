# skill-maintenance

`~/.claude/skills/*/SKILL.md` を編集するときの方針。新規作成は `skill-creator` を使う。ここは既存 skill の手入れ専用。

## 編集方針

### 1. 時系列ログを残さない

skill は「今の最良解」を書く場所。試行錯誤の履歴は git log に任せる。

**削除対象**:

- 日付付き観測ログ、PR / issue 番号への参照
- 「以前は X だったが今は Y」「旧バージョンでは…」型の経緯
- 「実機で確認した」「動作確認済み」等の鮮度メタ情報
- 既に下した決定の後付け正当化（「〜するのが既定の安全側」等）
- 検証されていない機序の説明。規則は残し、推測された原因（「二重エスケープと tty 初期化の組み合わせ」等）だけ削る

**残すもの**:

- 最新の解決方法（手順・コマンド・プロンプト本文）
- pitfall（踏み抜きやすい落とし穴）とその回避策
- 採否の理由が将来判断に効く場合のみ、根拠を 1 行

判断基準: その行を消したとき、未来の自分が同じ罠を踏むか？ Yes なら残す。

### 2. 指示より罠を書く

フロンティア級モデルにとって、行動を縛る指示は能力を削る。禁止形は理由が落ちると転用が効かず、機序を書けば未知の類似状況にも当てられる。`✕ をしない` は `✕ をすると Y が起きる。だから Z にする` に書き換える。

命令形のまま残す例外が 2 つある:

- **権限・信頼境界**（本番 pane は読み取り専用、Bash で拒否された操作を send-keys で迂回しない、ユーザー所有 pane を kill しない）。モデルの知識ではなく「誰が決めるか」の問題なので、能力が上がっても境界は移らない。理由を 1 行添えると境界事例の判断は上がる
- **外部エージェントへ渡す契約文言**（codex への `git commit 禁止`、出力見出し規約）。相手に渡す文字列であり、価値は洞察ではなく曖昧さの無さ。逐語で保つ。その契約が要る理由を Claude 向けに 1 行添えるのは別レイヤなので残してよい

### 3. モデルが既に知っていることを書かない

方針 2 が残す行の書き方なら、こちらは行を残すかどうかの判断。

- 標準ツールの一般的挙動（`tail` が EOF まで入力をバッファする等）は 1 行で足り、理屈の説明は要らない
- 「ユーザーの割り込みを優先する」「出力を鵜呑みにしない」等の汎用的な作法
- 残すのはモデルの既定と違う選択に導く行だけ（「`--full-auto` は `--sandbox read-only` を黙って上書きする」等）

### 4. 実行可能性を検証する

SKILL.md のコマンドは、そのまま打てなければ意味がない。`scripts/` もレビュー対象に含める。

- **SKILL.md の記述を `scripts/` の契約（フラグ・デフォルト値・exit code・出力形式）と照合する**。ズレは双方向に直す。本文を実装に合わせるだけでなく、実装側のバグは実装を直す
- スクリプトは実際に走らせて確認する。副作用のある経路は無効化して（投稿系の閾値を上げる、周回数を 1 にする等）読み取り系だけ通す。異常系（引数不正、対象が存在しない）も 1 回は踏む
- **防御を「強化」しない**。ポーリングループへの `set -e` 追加のように、クリーンアップに見える変更が過渡的失敗への耐性を壊すことがある。失敗を握り潰している箇所は、意図的な許容か欠陥かを見極めてから触る
- コマンド例は静的に検算する（マウント元と参照先、相対パスと cwd、変数の定義位置）
- 副作用なく打てるもの（`-h`、列挙系）は実走して確認する
- デフォルト値は使用箇所に書く。別節の default を読者が辿る前提にしない
- 統合・一般化した記述が元より広い主張になっていないか確認する。適用範囲を広げるなら、その分岐に効く前提（引数・フラグ）を使用箇所に併記する

### 5. スコープ外の固有名詞を一般化する

グローバル skill には特定案件の固有名詞（クラス名、ホスト名、インフラ構成、個別インシデントの再発防止項目）が混ざりやすい。転用できる観点だけ残し、事例は落とす。

### 6. フィラーを削る

- 同じことを 2 回書かない。節をまたいで重複したら統合する
- 「〜してください」「〜が推奨されます」を削り、命令形で短く
- 箇条書きの各項目は 1 行を目標に。2 行を超えるなら節に切り出すか削る
- 例示は 1 個に絞る（最良の 1 個 + pitfall に集約）
- 「使用例」「実行手順」の節は本文の再掲になりやすい。重複分は消す
- 見出しは内容を予測できる名詞句に

## 矛盾の是正

「反論の余地がある指示」は圧縮より優先して直す。典型:

- 同種の数値が別々の意味で登場する（ポーリング周回の上限 18 と対応サイクルの上限 10 等）→ 別物なら命名して区別する
- 本文の例と注意書きが食い違う（`./scripts/...` という例と「cwd 相対で呼ぶな」の併記）
- 実挙動より強い説明（「ssh している pane だけ」が実際は出力行全体の文字列一致）

## 作業手順

1. 対象 skill の SKILL.md 全文と `scripts/` を読む（スクリプトは挙動の確認だけでなく欠陥の摘出も行う）
2. 時系列要素・重複・矛盾・実行不能なコマンドを抽出する。ユーザーが「履歴として残す」と指定した節は対象外
3. 方針を先に受け取っていれば編集して事後報告。方針抜きの依頼なら編集案（削除・統合・短縮）を提示して確認を取る
4. 収束チェック: 行数と構造、frontmatter の `description` と本文の整合、削除した節の情報の移設先
5. 報告する。統合（fold）した節は移設先を明示する。読者からは削除と区別がつかない

複数 skill の一括メンテは skill 単位で順に処理する。並行編集は差分管理が破綻する。

## pitfall

- **frontmatter は本文と別の契約で動く**。`name` は skill 参照の slug なので、変えると呼び出し側が解決できなくなる。`description` のトリガー一覧は呼び出し精度そのもので、冗長に見えて削ると skill が起動しなくなる。本文のリーン化の基準をそのまま当てない。
- **過去の圧縮率を次回の目標にしない**。率を追うと pitfall が削られる。
- **pitfall 自体をログ扱いしない**。「過去に踏んだ罠だから消す」は誤り。再発防止に効くものは保持。
- **強調は不可逆な操作に優先配分する**。全部平文化すると優先度の山が消え、撒きすぎても同じ結果になる。ファイル内で最も危険な 1〜2 行に残す。
- **宙に浮いた参照を残さない**。「過去メモ参照」「前述のとおり」の参照先が本文に無ければ、事実を inline するか参照ごと消す。
