## あなたのタスク

$ARGUMENTS の日時以降、あるいは期間のコミットログから進捗報告を作成して下さい。
$ARGUMENTS がなければ本日、あるいは直近の一日から作成してください。

## 進捗報告のガイドライン

- フォーマットはプレーンテキスト形式。
- git log の取得では `--oneline` を付けずコミットメッセージの詳細まで確認する。ただしソースコードの差分まで確認する必要はありません。
- 規模の大きなコミットは、変更の影響度の大きさ順にまとめる。ただし、レポート中に "最高影響度" のような評価結果は出力しない。
- 些細な修正は簡潔にまとめる。
- 上記以外はコミットの時系列でまとめる。
- レポート中に "完全実装" や "完全解消" といった誇大なレポートは行わない。
- 実装の詳細（クラス名やソースファイル名）に立ち入った表現は控える。"◯◯の機能に対する□□の追加"といったような外形的な表現を心がける。

## 分量と書きぶり

読み手は非エンジニアであり、長い文章は読まれない。**短さを品質の一部として扱う。**

### 「変更の要約」の書き方

- **1 項目 1 行、40〜60 文字程度**。原則として句点で終わる 1 文に収める
- 「何が良くなったか」を主語にする。原因の機序・実装方式・却下した案は書かない
- コミットメッセージの論証（「〜のため」「〜が成立しないため」）は**理由が読み手の判断を変えるときだけ**残し、通常は落とす
- 専門用語はふだんの言い回しに置き換える（例: state → 状態 / cascade → 連動して / 冪等 → 何度実行しても同じ）

  悪い例:
  - 退会時にアフィリエイター側のペルソナへも波及するよう修正。ペルソナだけ生き残ると成果報酬が積み上がり続けるため

  良い例:
  - 退会するとアフィリエイター登録も一緒に解除されるように

### 「補足詳細」（子箇条書き）

- **原則として書かない。** 親の 1 行で伝わらないときだけ例外的に使う
- 例外として認めるのは次のいずれか
  - 件数・容量・日付などの実測値（例: 対象は 21,531 件）
  - 読み手が次に動く必要がある事項（残作業、要判断、運用手順）
- 例外を使う場合も **1 親につき 1 行まで**

### 全体の目安

「今北産業」に倣い、**3 行までなら読まれる**を上限とする。

- **テーマは 3 つまで。** 期間内で比重の大きかったものを選び、残りは省略する
- **1 テーマあたり 3 項目まで。** 4 行以上の箇条書きは読まれない
- 上限は目標ではない。2 つ / 2 項目で足りるならそれでよい
- 省略したものは「その他」として、Issue / PR 番号のリンクを列挙するだけに留める

### Issue / PR リンク

**レポートはメールで配布するため、`#1417` のような番号は自動リンクされない。**
本文中は番号で参照し、末尾の「参照」ブロックに完全な URL を列挙する。

- 本文中は `(#1417)` の形式。本文に URL を直書きしない（行が長くなり読みにくい）
- 末尾に `参照` ブロックを置き、`#1417 https://github.com/{owner}/{repo}/issues/1417`
  の形式で 1 行 1 件を列挙する。owner/repo は `git remote get-url origin` から取る
- Issue と PR の両方がある場合は Issue を優先する。PR しか無いものは PR 番号を書き、
  URL は `/pull/{番号}` にする
- **テーマ内の項目が同じ番号を指すなら見出しに寄せる**（例: `会員退会機能 (#1417)`）。
  同じ番号を項目ごとに繰り返さない
- 項目ごとに番号が違う場合のみ、各項目の末尾に添える
- 複数ある場合は主要なものを 1〜2 個に絞る

## 概況の作り方

ヘッダー（対象期間・コミット数）と最初の `---` の間に「概況」ブロックを置く。
コミット単位の羅列では見えない「この期間は何をしていたのか」を、
受け取る側が数秒で読み取れる分量で示す。

### 分量の制約

- **通常は 1 トピック、多くても 2 トピックまで**。期間内で最も比重の大きかったものを選ぶ
- **全体で 1 段落に収まる分量**に留める。箇条書きにする場合も 1 行 1 トピックで最大 2 行
- 網羅は目的ではない。詳細は後続のテーマ節が担うので、概況では触れずに落としてよい

### 何を書くか

次のいずれかから、その期間を最もよく表すものを選ぶ。**全部を埋めない**。
テンプレートの観点は選択肢であって、必須項目ではない。

- その期間の作業が集中していたテーマ
- 決着した課題（原因が特定できた／対処が入った）
- 判明した未解決の課題（次に持ち越す事項）
- 着手した新規の機能・仕組み・運用

### 情報源

1. **コミットログ本文**が一次ソース。まずここから概況を組み立てる
2. 補助的に**セッションメモリ**（`~/.claude/projects/<project>/memory/`）と
   **hindsight**（`hindsight_search_knowledge_pages` / `hindsight_reflect`）を参照し、
   コミットメッセージだけでは見えない背景・経緯・未解決事項を補う

### hindsight / メモリ利用時の注意

- **他プロジェクトの情報を混ぜない**。hindsight の recall / reflect は横断的に応答しうるため、
  取得結果が本レポート対象のリポジトリの作業かどうかを必ず確認してから採用する。
  リポジトリ名・issue 番号・コミットとの対応が取れないものは採用しない
- **期間外の情報を混ぜない**。メモリや knowledge page は過去の状態を含むため、
  対象期間内の出来事として書けるものだけを採る
- コミットログで裏が取れない記述は「〜と見込み」「未検証」のように確度を落として書くか、落とす
- 概況ブロックに hindsight のクレジット blockquote（🧠 見出し）は入れない。
  レポートはプレーンテキストの成果物であり、出典表記は不要

## 出力テンプレート

以下の構造に従って出力する。インデントは半角スペース2つ。

```
{プロジェクト名}

進捗報告（{対象期間}）
対象期間のコミット数: {N}件

概況

{その期間を最もよく表すトピックを 1 つ、多くても 2 つ。全体で 1 段落程度}

---
{テーマ見出し1} (#{Issue番号})

- {変更の要約}
- {変更の要約}

---
{テーマ見出し2}

- {変更の要約} (#{Issue番号})
- {変更の要約} (#{Issue番号})

---
{テーマ見出し3（任意）}

- {変更の要約} (#{Issue番号})

---
その他

{省略したものの Issue / PR 番号を 1〜3 行で列挙}

---
参照

#{番号} {URL}
#{番号} {URL}
```

### テンプレート運用ルール

- **ヘッダー**: プロジェクト名 → タイトル行 → 対象期間・コミット数の順。コミット数が少ない場合は変更ファイル数・行数を添えてもよい
- **概況**: ヘッダー直後、最初の `---` の前に置く。トピックは通常 1 つ、最大 2 つ。全体で 1 段落に収める。散文でも 1〜2 行の箇条書きでもよい
- **セクション区切り**: テーマ間は `---` で区切る
- **テーマ見出し**: 関連するコミットを意味のあるまとまりでグルーピングし、見出しを付ける。3 つまで。テーマ全体が単一の Issue に対応するなら見出しに番号を添える
- **サブ見出し**: 原則使わない。テーマを 3 つ以内に絞れば不要になる
- **項目の書式**: 各項目はハイフン箇条書きで 1 行。補足の子箇条書きは「分量と書きぶり」の例外条件を満たすときのみ
- **少数コミットの場合**: 番号付きリスト（`1.` `2.`）で時系列順に並べ、各項目にコミット時刻を添えてもよい
- **まとめ**: 概況を冒頭に置くため、末尾の総括は原則不要。付ける場合も1行に留める
- **参照**: 最後のブロック。本文に出た番号をすべて、出現順に URL 付きで列挙する
