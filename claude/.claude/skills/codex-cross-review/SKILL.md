# codex-cross-review

Codex CLI（OpenAI）にクロスレビューを依頼するスキル。Claude 自身の作業へのセカンドオピニオン用途。レビュー以外の相談・バグ調査・分析・提案は対象外。

## 実行モード

判定優先順:

1. 「再レビュー」「resume」「更新したからもう一回見て」 → モード2
2. 「1 回だけ」「単発」「とりあえず見て」 → モード1
3. それ以外 → モード3（収束ループ、デフォルト）

### モード1: 単発レビュー

`--cd` には対象プロジェクト dir（未指定なら現在の cwd）を渡す。プロンプト本文には「プロンプトのルール」の必須指示 4 つを含める。

```bash
timeout 600 codex exec --sandbox read-only --cd <project_dir> - <<'PROMPT' 2>&1 | tail -120
<プロンプト本文>
PROMPT
```

- `--full-auto` は `--sandbox read-only` を黙って `workspace-write` に上書きする。`codex exec` は元々 `approval: never` の非対話実行なので、`--sandbox read-only` だけで足りる。
- バナーの `sandbox: read-only` と `session id: <uuid>` を確認する。session id は再レビューで使うので控える。

### モード2: 再レビュー（resume）

直前の Codex セッションのコンテキストを引き継ぐ:

```bash
timeout 600 codex exec resume <SESSION_ID> - <<'PROMPT' 2>&1 | tail -120
<プロンプト本文>
PROMPT
```

- `--last` はマシン全体で最後の codex セッションを拾う。別プロジェクトや codex-yolo-implement の実装セッションが挟まると取り違えるので session id 指定を優先する。
- resume は `--cd` / `--sandbox` を受け付けない（unexpected argument エラー）。sandbox 等は元セッションから引き継がれる。変えたいときは `-c key=value`。

### モード3: 収束ループ（デフォルト）

1. モード1 と同形のコマンドで新規レビュー（session id を控える）
2. 結果を「結果のトリアージ」でフィルタし、残った提案を「スコープ膨張ガード」にかける
3. 残った重要指摘を報告 → 修正
4. モード2（resume）で再レビュー
5. 終了条件は以下の両方を満たすこと:
   - 重要指摘がゼロ
   - 直近イテレーションで新規ファイル / 新規概念の追加なし（または追加分はユーザー承認済み）

初回レビューで指摘ゼロが返り、トリアージ後も残件なしなら、モード2 を呼ばずに収束として報告してよい。

## プロンプトの渡し方

`-` + quoted heredoc で stdin から渡す。インライン引数だとプロンプト中のバッククォートや `$()` が bash のコマンド置換で壊れ、引数渡しのつもりが stdin 待ちの無音ハングに入ることもある。

```bash
codex exec --sandbox read-only --cd <dir> - <<'PROMPT'
（バッククォートも $ もそのまま書ける）
PROMPT
```

長大なプロンプトはファイル経由でもよい: `codex exec ... - < /tmp/codex-prompt.md`

- stdin を渡していないのに `Reading additional input from stdin...` のまま止まったらハング。kill して stdin 方式で再投入する（stdin を渡している状態でのこのログは正常）。
- ハング判定は出力ログのサイズ成長と `ps -o pid,etime,time` の CPU 時間。ログが伸びているなら時間がかかっているだけ。

## 実行時間と待ち方

起動に数十秒、レビュー完了まで数分〜10 分。

- フォアグラウンド: `timeout 600`（複雑な diff は 900）+ Bash の timeout を 600000〜900000ms。
- バックグラウンドは stdout を取りこぼしうる。`-o <FILE>` で最終レスポンスをファイルに確定保存するか、`> /tmp/codex-out.log 2>&1` にリダイレクトする。

## プロンプトのルール

codex に渡すリクエストに以下をすべて含める:

1. 「些細な点への指摘はせず、致命的・本質的な点だけ指摘して。」
2. 「確認や質問は不要です。具体的な提案・修正案・コード例まで自主的に出力してください。」
3. 「元 spec の『含まないもの』に挙がっている事項を覆す提案、および新規ファイル・新規抽象化・新規設定キーの追加提案は、観測された障害ではなく仮説に基づく場合は『致命的』に分類しないこと。」
4. 「ドキュメント・コメント・plan/spec の文面に対する指摘は、実装との食い違いや事実誤り等の明白な誤りに限ること。言い回し・構成の好み、記述の掘り下げ、内容として正しいだけの補足の提案はしないこと。」

(3) がないと「あった方がよい」「将来必要かも」級の YAGNI 違反提案が「致命的」フレーミングで出て、収束ループで spec/plan が膨張する。(4) がないと散文に対して無限に指摘が出て収束しない（散文には正解が無い）。

網羅的なレビューが欲しいときは (1) を「致命的な点に加え、改善点も漏れなく指摘して」に差し替える。

### 構成テンプレ

```
<何を>レビューして。

背景: <なぜこの変更をしたか。バグ修正なら真因の説明>

レビュー対象:
- 絶対パスでファイル列挙、または「origin/main..HEAD（ブランチ <name>）の diff」と range 指定
  （range 指定なら codex が自分で git diff を読む）

重点的に見てほしい点:
1. <設計の核となる前提が正しいか>
2. <競合・境界条件>

<必須指示 1〜4>

参考: (ref: /path/to/CLAUDE.md) (ref: /path/to/plan.md)
```

レビュー対象ファイルは絶対パスをそのまま記述する（codex が自動的に読む）。補足コンテキストは `(ref: /path/to/file)` で渡す。

## パラメータ

| パラメータ | 説明 |
|-----------|------|
| `--sandbox read-only` | 読み取り専用サンドボックス。レビューはこれで固定 |
| `--cd <dir>` | 対象プロジェクトのディレクトリ |
| `-` + heredoc / `< file` | プロンプトを stdin から渡す |
| `resume <SESSION_ID>` | 指定セッションを引き継ぐ（`--last` は取り違えリスクあり） |
| `-c key=value` | config.toml の値を上書き |
| `-o <file>` | 最終レスポンスをファイルに保存（bg 実行時の取りこぼし対策） |

## 結果のトリアージ

**重視する（ユーザーに伝える）**: 致命的なバグ・ロジックエラー / セキュリティ上の問題 / データ損失・破壊のリスク / 仕様との明確な矛盾。

**建設的に無視する**

- 些細なスタイル・命名の好み
- 過剰な共通化・DRY の押しつけ（3 回未満の重複は放置でよい）
- 時期尚早な最適化、「こうした方がベター」級の主観的改善案
- 既存コードベースの慣習と合わない提案

### 非コード指摘ガード（ドキュメント / コメント / plan / spec の文面）

対象が散文なら採用は **明白な誤り** だけ。

- 採用: 実装・決定事項と食い違う / 事実誤り（値・パス・手順・API 名）/ 読んだ人が操作や判断を間違える曖昧さ / リンク切れ
- 反証: 言い回し・構成・トーンの好み / 掘り下げ要求 / 正しいだけの補足追加 / 「〜にも触れるべき」

散文には正解が無く、codex は無限に指摘を出せる。同一ファイルの散文指摘が 2 イテレーション目に入ったら個別評価せず一括で打ち切り、モード3 の「重要指摘ゼロ」として扱う。

### スコープ膨張ガード

トリアージを通った提案でも、以下のいずれかに該当するものは自動採用しない。ユーザーに採否を確認する。

- 元 spec の「含まないもの」セクションを実質的に巻き戻す
- 新規ファイル / 新規抽象化 / 新規設定キーを追加する
- 観測されたバグではなく仮説的な失敗モードへの先回り対処

採用する場合も、並行性・状態遷移・ジョブのライフサイクルに触れる提案は新しいリグレッションを持ち込みうる。採用後に regression テストか実走で独立に検証する。codex の OK は検証の代わりにならない。
